# Sub-project B: Toolgate Gateway — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One authenticated MCP endpoint that aggregates the three sub-project A servers. It shows each agent only its allowlisted, pin-verified tools, blocks drifted or unpinned tools and smuggled arguments, scans outputs, and writes every call to an append-only audit log with tracing.

**Architecture:** A Python MCP proxy on the official SDK's low-level `Server`, served over streamable HTTP behind the SDK's bearer-auth middleware. Requests flow agent → `GatewayCore`. The core verifies against `toolgate-pin`'s `Pinner` (using the lockfile from sub-project C), checks per-agent allowlists, validates arguments against the pinned schema, routes to pooled downstream `ClientSession`s using the gateway's own client-credentials tokens, scans outputs with `toolgate_pin.scan_output`, and sends audit records to Postgres through a batched writer that fails closed. Each stage gets an OpenTelemetry span exported to Tempo.

**Tech Stack:** Python ≥3.12 (workspace), `mcp>=1.12,<2` (1.30.0 locked), `toolgate-pin` (workspace), PyJWT[crypto], httpx, asyncpg, jsonschema, PyYAML, pydantic-settings, rfc8785, opentelemetry-sdk + otlp exporter; Keycloak 26, Postgres 16, Grafana Tempo + Grafana (compose); pytest, testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-18-toolgate-design.md` §2, §3 (storage and allowlists), §4 (request flow, auth, latency, failure posture). It builds on `docs/superpowers/specs/2026-10-18-subproject-c-toolgate-pin-design.md` §5.4 (Pinner API).

## Decisions made without a brainstorm (the user skipped questions; these are Claude's calls)

1. **Pins come from the git-committed lockfile** (`toolgate.lock.json`, sub-project C), not from a Postgres `tool_pins` table. Approval is `toolgate-pin approve` plus a commit. The gateway hot-reloads the lockfile when it changes. Postgres holds only `audit_log` and `pending_reviews`. This deviates from umbrella §3's tables, and it supersedes the plan in C to build a Postgres `PinStore` here.
2. **Namespaced tool names:** `<server_id>.<tool>`, e.g. `core-read.get_claim_status`.
3. **Allowlists:** `policy/agents.yaml` maps a Keycloak client id to exact or `fnmatch` glob patterns of namespaced names. Deny by default.
4. **Downstream identity:** a new Keycloak client `toolgate-gateway` whose tokens carry `aud` = core-read, core-write and comms. Three agent clients (`servicing`, `claims-intake`, `fraud-triage`) get `aud=toolgate-gateway`.
5. **One verified snapshot shared by all callers.** It is refreshed on every `tools/list`, on downstream `list_changed`, and at startup. `tools/call` only consults the snapshot.
6. **Low-level SDK server**, not FastMCP, because tool lists are dynamic per caller.
7. **MCP SDK stays 1.x**, as ruled in sub-project A.

## Global Constraints

- New workspace package `packages/toolgate-gateway`, import `toolgate_gateway`, console script `toolgate-gateway`, src layout, hatchling.
- No token passthrough. The agent's token never leaves the gateway. Downstream calls use the `toolgate-gateway` client's own token, cached until 30 s before expiry.
- Agent tokens: RS256, local JWKS verification; check `iss`, `aud` (= `toolgate-gateway`), `exp`, `azp`. Unauthenticated → HTTP 401 with `WWW-Authenticate` and RFC 9728 protected-resource metadata.
- Audit `decision` values exactly: `allow`, `deny_unknown_tool`, `deny_scope`, `deny_unpinned`, `deny_drift`, `deny_schema`, `deny_output`, `flag_output`, plus `error_downstream` (Claude's call: downstream failure after an otherwise-allowed call).
- `args_hmac` = hex HMAC-SHA256(key=`AUDIT_HMAC_KEY`, msg=RFC 8785 canonical JSON of the arguments). Raw arguments are never stored.
- The application DB role has INSERT only on `audit_log`, never UPDATE or DELETE.
- Fail closed:
  - Audit queue full or DB unwritable → deny the call.
  - Lockfile unreadable → keep the last good pins for ≤ 5 minutes (`PIN_STALE_SECONDS = 300`), then list no tools.
  - JWKS fetch fails → use cached keys.
  - A downstream that is down has its tools omitted, and calls to it return a tool error.
- The audit writer flushes every 100 ms or 50 rows. The queue bound is `AUDIT_QUEUE_MAX = 10_000`.
- Downstream call timeout is 30 s, with the client's cancellation passed through.
- Trace attributes are names, hashes, decisions and client ids only. Never arguments, results, descriptions or tokens.
- Secrets live only in `.env`, generated by `scripts/gen_dev_env.py`. The committed realm template has placeholders. Each container receives only its own secrets (sub-project A convention).
- Run everything via `uv run` in the repo-root `.venv`. pre-commit must pass. Each commit ends with the writing model's own `Co-Authored-By` trailer.

## Review Focus

1. **An expired agent token, or a token for the wrong audience** (e.g. a `core-read` audience token presented to the gateway): 401, and nothing is forwarded downstream. Test in Task 7.
2. **A downstream that is down at startup, or dies mid-session:** its tools disappear from `tools/list`. Calls return an `isError` result with `error_downstream`. The gateway keeps serving the other servers and reconnects on the next list. Tests in Tasks 4 and 6.
3. **The lockfile edited while the gateway runs:** a valid edit is picked up on the next `tools/list`. A corrupt edit keeps the last good pins until 300 s have passed, then lists nothing. Test in Task 5.
4. **Argument smuggling:** extra properties, wrong types, or a 1 MB argument. Gives `deny_schema` before any downstream call. The audit row stores only the HMAC. Test in Task 6.
5. **Postgres down or the audit queue saturated:** `tools/call` is denied with a clear tool error. `tools/list` still works, since listing is not audited. Tests in Tasks 3 and 6.

### Task 3: Audit log and pending reviews in Postgres

  - `async record(server_id, tool_name, observed_hash, pinned_hash, reason, diff, findings: list[dict]) -> None`: upserts and bumps `last_seen`.
  - `async resolve_pinned(pins: PinSet) -> int`: marks open rows resolved when the observed hash is now pinned.
  - `async list_open() -> list[dict]`.

### Task 5: `GatewayCore.list_tools` — pins, snapshot, allowlist, reviews

**Files:** Create `src/toolgate_gateway/{pins,core}.py`, `tests/test_pins.py`, `tests/test_core_list.py`

**Interfaces:**
- `PinSource(path: Path, *, stale_after_s: float = 300.0, clock=time.monotonic)`:
  - `current() -> PinSet | None`. It re-reads only when the file's `(mtime_ns, size)` changed. On `LockfileError` it keeps the last good PinSet, and once that is older than `stale_after_s` it returns None.
  - `pinner() -> Pinner | None` returns a `toolgate_pin.Pinner(InMemoryStore(pinset))` rebuilt on change.
- `SnapshotEntry(server_id, tool: Tool, namespaced: str, tool_hash: str, input_validator)`. The validator is `jsonschema.Draft202012Validator` over the pinned `inputSchema`, compiled once per hash. If the pinned schema lacks `additionalProperties`, enforce `additionalProperties: false` at the top level.
- `GatewayCore(pool: DownstreamPool, pins: PinSource, allowlist: Allowlist, audit: AuditWriter, reviews: PendingReviews | None, *, hmac_key: str)`.
- `async list_tools(client_id: str) -> list[Tool]`:
  1. Fetch all downstreams in parallel.
  2. Run `Pinner.verify(server_id, tools, server_info=info)` per server.
  3. Record a pending review for every quarantine (`drift`, `unpinned`, `server_drift`; `removed` is skipped) with diff and findings. Log a structured `toolgate.alert` warning and add a span event.
  4. Rebuild the snapshot from `allowed`.
  5. Call `reviews.resolve_pinned`.
  6. Return the allowed snapshot entries the client is allowlisted for, as namespaced `Tool` copies (`name` replaced; everything else verbatim).

  Reviews failures are logged and never fail the list.
- `async refresh_snapshot() -> None` runs the same logic with no client filter. It is used at startup and by `on_list_changed`.

### Task 6: `GatewayCore.call_tool` — decisions, schema, output scan, audit

**Files:** Modify `src/toolgate_gateway/core.py`. Create `tests/test_core_call.py`.

**Interfaces:**
- `async call_tool(client_id: str, agent_id: str, name: str, arguments: dict | None) -> CallToolResult`. `agent_id` is the token's `sub`, or `client_id` if there is no `sub`.
- Decision order. The first failing step returns an `isError=True` result whose text is a fixed message (it never echoes arguments), and audits that decision:

  | Order | Check | Decision on failure |
  |---|---|---|
  | 1 | `split_namespaced` fails, or the server_id is unknown | `deny_unknown_tool` |
  | 2 | Not allowlisted | `deny_scope` |
  | 3 | Not in the snapshot. If the tool is pinned for the server but the snapshot's hash differs, this is `deny_drift` instead | `deny_unpinned` |
  | 4 | The validator fails | `deny_schema` |
  | 5 | The audit writer is unhealthy or its queue is full (checked before forwarding) | No audit row (the audit itself is down). Return the error "audit log unavailable; call refused" and log the refusal. |
  | 6 | Forward via the pool. `DownstreamUnavailable` → `error_downstream` | `error_downstream` |
  | 7 | `scan_output(result, server_id=…, inventory=snapshot inventory)`: `malicious` → replace with the error "tool output withheld by policy" | `deny_output` |
  |   | `suspicious` → pass through | `flag_output` |
  |   | otherwise | `allow` |
- Every audited row carries `tool_hash` (snapshot hash, or None), `args_hmac`, `latency_ms` (gateway overhead plus downstream) and `trace_id`. Audit is the final step; `submit` returning False after forwarding is logged as an audit drop.
